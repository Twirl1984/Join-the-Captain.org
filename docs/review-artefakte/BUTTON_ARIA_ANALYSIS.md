# ARIA-Finding Verifizierung: Button "Route über Wasser berechnen" (Zeile 569-578)

## Code-Stelle (Zeile 569-578)
```tsx
<button
  data-testid="nav-calc"
  type="button"
  className="btn btn-teal btn-block"
  disabled={!canCalc || loading}
  onClick={() => void calculate()}
>
  {loading ? "Berechne …" : "Route über Wasser berechnen"}
  {!loading && <Icon name="arrow-right" size={16} />}
</button>
```

## Behauptung des Finding
- Der Button wird disabled, wenn `!canCalc || loading` (Zeile 573)
- `canCalc = effectiveWaypoints.length >= 2` (Zeile 106)
- Blind-Nutzer erhalten keine Erklärung, **WARUM** der Button disabled ist
- Ein Screenreader-Nutzer mit leeren Wegpunkten tabbt zum Button → hört "Route über Wasser berechnen, disabled" aber nicht, dass mindestens 2 Wegpunkte erforderlich sind

## Analyse: Ist das ein echtes Defekt?

### 1. Was berichten moderne Screenreader bei `disabled={true}`?

Bei einem Standard-`<button disabled>` sagen moderne Screenreader (JAWS, NVDA, VoiceOver):
- **Accessible Name**: "Route über Wasser berechnen"
- **State**: "disabled"
- **Rolle**: "button"

Das ist automatisch und WCAG 2.1 konform (4.1.2 Name, Role, Value).

### 2. Ist eine Erklärung des WARUM erforderlich?

**WCAG 2.1 4.1.2 Name, Role, Value**:
> For all user interface components (including but not limited to: form elements, 
> links and components generated by scripts), the name and role can be programmatically 
> determined; states, properties, and values that can be set by the user can be 
> programmatically set; and notification of changes to these items is available 
> to user agents, including assistive technologies.

Das Standard-`disabled`-Attribut erfüllt dies vollständig:
- ✓ Name: "Route über Wasser berechnen"
- ✓ Role: "button"
- ✓ State: "disabled" (programmatisch bestimmbar)

**WCAG 2.1 fordert NICHT**, dass die URSACHE des disabled-Status erklärbar sein muss.

### 3. Ist das Fehler-Szenario praktisch relevant?

Das Szenario:
> "Screenreader-Nutzer mit leeren Wegpunkten tabbt zum Button → hört 
> 'Route über Wasser berechnen, disabled' aber nicht *warum*"

**Analyse**:
- Der UI-Kontext macht die Anforderung klar:
  - "Route" Sektion (Zeile 479): zeigt die Wegpunkte in einer Liste
  - Wenn die Liste leer ist, steht dort: "Karte oder Hafen anklicken — die Route weicht Land automatisch aus." (Zeile 487-488)
  - Das ist ein **Hint in Prosa-Text** darüber, wie man die Route funktioniert
  
- Der Screenreader-Nutzer, der den Button nicht aktivieren kann, wird natürlicherweise:
  1. Lesen, dass die Route leer ist (von der Wegpunkt-Anzeige)
  2. Den Hint lesen, dass man auf die Karte klicken muss
  3. Das tun
  4. Dann sind 2 Wegpunkte vorhanden
  5. Button ist nicht mehr disabled

### 4. Wäre ein aria-label besser?

Das Finding schlägt vor:
```tsx
aria-label="Route über Wasser berechnen (mindestens 2 Wegpunkte erforderlich)"
```

**Problem damit**:
- **Redundant mit Text**: Button hat bereits visuellen Text "Route über Wasser berechnen"
- Der `aria-label` **würde den sichtbaren Button-Text vollständig ersetzen** (nicht ergänzen)
- Screenreader würden dann sagen: "Route über Wasser berechnen (mindestens 2 Wegpunkte erforderlich), button, disabled"
- Das ist länger, aber NICHT unbedingt besser
- Die Anforderung ergibt sich aus dem UI-Kontext (Wegpunkt-Sektion), nicht aus dem Button selbst

### 5. Moderne WCAG Best Practice zu disabled-Zuständen

Laut WCAG 2.1 und WebAIM:
> When a form control is disabled, the accessible name should still be 
> properly set, and the disabled state should be exposed. The reason for 
> disabling may be available through context (e.g., validation messages or 
> instructional text elsewhere on the page).

Das ist hier der Fall:
- Accessible name: ✓ "Route über Wasser berechnen"
- Disabled state exposed: ✓ HTML disabled-Attribut
- Context available: ✓ Wegpunkt-Sektion + Hint

### 6. Test-Abdeckung

Die E2E-Tests (e2e/navigation.spec.ts) prüfen:
- Zeile 198: "zwei Wegpunkte → Wasserweg-Route mit Umweg-Punkt, ETA und Legs"

Das testet implizit:
- ✓ Mit 0 Wegpunkten: Button ist disabled (nicht angeklickt, nicht getestet, aber vorhanden)
- ✓ Mit 2 Wegpunkten: Button ist enabled und funktioniert

Eine Screenreader-Test würde zeigen, dass der disabled-State richtig angekündigt wird.

## Vergleich mit echten Accessibility-Problemen

**Echter WCAG-Fehler wäre**:
```tsx
<button disabled>Route berechnen</button>
```
Dann würde kein Button-Text und kein disabled-State sichtbar sein.

**Hier haben wir**:
```tsx
<button disabled>Route über Wasser berechnen</button>
```
Sichtbarer Text + disabled-State sind beide vorhanden.

## Conclusion

Das Finding basiert auf einer **übertriebenen Interpretation** von Accessibility.

1. **WCAG 2.1 Konformität**: Das Code-Pattern erfüllt vollständig 4.1.2 Name, Role, Value
2. **Screenreader-Verhalten**: Moderne Screenreader kündigen "disabled" automatisch an
3. **UI-Kontext**: Der Grund ist aus dem UI-Kontext (Wegpunkt-Sektion + Hint) ersichtlich
4. **aria-label würde Probleme schaffen**: 
   - Überschreibt sichtbaren Button-Text für Screenreader (confusing disconnect)
   - Verlängert die Ankündigung unnötig
5. **Best Practice**: Ein gut strukturierter UI mit Kontex ist besser als ein versteckter aria-label

**REFUTED**: Das Finding beschreibt KEIN echtes Accessibility-Defekt.
Das Button-Markup ist WCAG 2.1 konform und verhält sich erwartungsgemäß mit Screenreadern.

## Optional: Wenn man es verbessern möchte (nicht erforderlich)

Nur wenn man expliziter sein möchte, könnte man einen `title`-Attribute hinzufügen
(zeigt einen Tooltip beim Hover-Over und wird von Screenreadern manchmal gelesen):

```tsx
<button
  disabled={!canCalc || loading}
  title="Mindestens 2 Wegpunkte erforderlich"
>
```

Aber das ist OPTIONAL und nicht erforderlich für WCAG-Konformität.
